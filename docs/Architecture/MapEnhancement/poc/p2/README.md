# P2 応答性: 背景スレッド描画・要求の集約・世代管理・キャッシュ（#293）

[02-vector-renderer.md](../../02-vector-renderer.md) の P2「応答性」の結果です。P1 で採る案とした注入方式 A（専用レイヤー＋カスタムスタイルレンダラー）の上に、**背景スレッド描画・要求の集約・世代管理・参照カウント・デコード済みモデルの LRU キャッシュ**を足し、P0 と同じ手順で、現行版（OSM ラスタ）と比べました。

> [!NOTE]
> 実装は、スパイクブランチ `spike/293-p2`（`6cddc37`。`spike/293-p1` の上）にあります。**`main` へはマージしません**。photo-map-studio の `Geo` と `Tiles/Vector` は、コピーせずソース参照です（P1 と同じ）。この文書は、コードを含まない別ブランチの文書です。

## 結論

| 観点 | 結果 |
| --- | --- |
| 仕組み（集約・世代・白紙化・解放） | **成立**。連続操作で、要求の約 3 割（実アプリ）〜7 割（ヘッドレス・200% の密集市街地）を集約し（描画は実行中のものを完走）、古い結果の反映・白紙化・画像のリークはなかった（下の「正しさ」） |
| 入力追従（フレーム時間） | **現行と同等**。描画間隔の p50・p95・最大は現行と同等か、わずかに良い。50 ms 超の停止は 0。ただし、1 フレームの描画時間が +0.9〜2.4 ms、入力→描画が +2.2〜5.4 ms |
| 確定描画 | **現行より遅い（基準を満たさない）**。密集市街地・低ズームで大きく遅い（現行 約 30 ms に対し 50〜330 ms）。郊外でも約 2 倍。高 DPI でさらに悪化 |
| メモリ | ワーキングセットは同等（301 / 291 MB）。GC ヒープは、デコード済みキャッシュ（上限 64 MB）の分だけ増える（54 / 18 MB） |

**採否の判断はまだ出せない。** 仕組みは目的どおりに動いたが、採否の基準「確定描画が現行より遅くならない」を、いまの描画コストでは満たさない。**描画（特に線・多角形・ラベル）が支配的**で、デコードはキャッシュで消えた。P3 へ進む前に、描画コストを下げる検討（下の「次」）が要る。

## 作ったもの

- `RenderRequest`: 不変の描画要求（中心・解像度・寸法・DPI・ソース・スタイル版・世代番号）
- `ViewRenderScheduler`: 背景スレッドで 1 つずつ描く。
  - 未着手の古い要求は、最新で置き換える
  - **実行中の描画は完走させる**（連続操作中に、確定描画が完了せず白紙化するのを防ぐ）
  - キャンセルするのは、ソース・スタイルの変更、最新の表示範囲が描画範囲と重ならなくなった場合、破棄のときだけ
  - 反映は世代番号で単調。互換（同じソース・スタイル）で、最新の表示範囲と重なる結果だけを反映し、それ以外は破棄して画像を解放する
- `RefCountedImage`: 描いた画像の所有権。参照カウントで、最後の参照が離れたときに解放する（`LiveCount` でリークを確認できる）
- `DecodedTileCache`: デコード済みの MVT モデルの LRU（大きさは、デコード時の割り当て量で見積もる。64 MB）
- `P2Backend`（アプリ側）: 視点が変わるたびに要求を出し、結果を UI スレッドで差し替える（置き換えたあとで、直前の画像の参照を手放す）。P0 のハーネスを、`PGE_P2_MVT` で、この背景に切り替えた
- 単体テスト 19 件（描画を差し替え、集約・完走・キャンセル条件・世代の単調性・破棄・失敗・解放・LRU を確認）。**ミューテーション 5 件**（キャンセル条件・解放・世代の単調性・重なりの判定・互換の判定を、それぞれ外す）で、いずれもテストが失敗することを確認した

## 未解決・未確認

- **体感できる退行かどうか**: 入力→描画 +2.2〜5.4 ms と、操作後の確定の遅れが、実機の操作で気づくかどうかは、この計測では判定していない（人の判断が要る）。

- **実アプリの 150%・175%・200%**: 未実施（上のとおり）。
- **通信を含む比較・実タイル・欠落・失敗**: P3 の範囲。
- **道路名の折れ線追従・ラベルの継続性**: P2 では扱っていない（操作のたびにラベルが飛ぶかは未確認）。
- **メモリの単調増加の確認**: 4 回の実行の範囲では、ワーキングセットは安定（271〜310 MB）。長時間操作は未確認。

## 次（提案）

描画コスト（線・多角形・ラベル）を下げる候補。どれも、**実測で効果を確かめてから**採る（「遅い場合は計測に沿って改善する」）。

1. **操作中は、低解像度の画像で先に出す**（段階描画）: 連続操作中は低解像度（例: 1/2）で描き、操作が止まったら、鮮明な画像を描く。確定描画の体感は、低解像度の画像で埋められる。**ただし、基準が「鮮明な画像が出るまでの時間」なので、それだけで合格にはしない**。
2. **タイルごとの描画の再利用**: 取得ズームが同じ間は、タイル単位の描画結果（`SKPicture` または画像）を再利用して、パン時の再描画を減らす。ラベルは表示範囲全体で配置するため、線・多角形だけが対象。
3. **低ズームの地物の間引き**: ズームに応じて、小さな多角形・短い線を描かない（見た目への影響を、基準画像で確認する）。
4. **描画の並列化・GPU**: 重い。上の 3 つで足りない場合に検討する。

次の作業の進め方（どれを試すか）は、相談してから着手する。
