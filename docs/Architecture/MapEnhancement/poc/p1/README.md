# P1 オフライン操作: 注入方式の比較と位置の整合（#293）

[02-vector-renderer.md](../../02-vector-renderer.md) の P1「オフライン操作」の結果です。保存済みの MVT で、Mapsui の中心・解像度に合わせた**表示範囲画像**を描いて地理範囲へ置き、パン・連続ズーム・リサイズ・DPI・複数ピンで位置が合うかを確認しました。あわせて、注入方式（カスタムスタイルレンダラー／`RasterFeature`）を比較しました。

> [!NOTE]
> 実装は、スパイクブランチ `spike/293-p1`（`b95166a`。`spike/293-p0-bench` の上。`main` へはマージしない）にあります。photo-map-studio の `Geo` と `Tiles/Vector` は、コピーせずソースのリンクで取り込みました（photo-map-studio `b856d7d`）。この文書は、取り込んだコードを含まない別ブランチで `main` に入れます。

## 結論

| 項目 | 結果 |
| --- | --- |
| 注入方式 | **A（専用レイヤー＋カスタムスタイルレンダラー）を採る案**。Mapsui 5.1.0 の公開 API だけで書けた（設計書のリスク「カスタムレンダラーが書けない」は解消）。B（`RasterFeature`）も動くが、更新ごとの PNG エンコードが重い |
| 位置の整合 | **成立**。実アプリで、DPI 100〜175%・静止・パン・拡大・縮小・連続倍率とも、十字と標識の相対ずれは多くが 1 px 以下。ただし、**縮小表示と 175% の連続倍率に、1.2〜2.9 px のずれが残る**（原因未特定。下記） |
| 連続倍率 | **成立**。`ViewExtentVectorRenderer` は、整数の取得ズーム（z14 の MVT）と連続の表示倍率を分けて、z15〜19 の任意の小数ズームで描ける |
| SkiaSharp 4.156.0 | 関門を通過済み。この実装も 4.156.0 で動いた |

**次（P2）へ進める**。ただし、下の「未解決・未確認」と「photo-map-studio 側に要る変更」を、P2 の入口の条件にする。

## 作ったもの

- `ViewExtentVectorRenderer`: 中心（緯度経度）・**連続ズーム**・画像寸法（物理ピクセル）で、表示範囲全体を 1 枚の `SKBitmap` に描く。photo-map-studio の `VectorMapRenderer`（整数ズームだけ）を元に、倍率を `double` にした。取得ズームは `min(floor(zoom), 14)`、表示倍率は `2^(zoom - 取得ズーム)`。スタイルの判定には `floor(zoom)` を渡す
- `SavedMvtTileSource`: 保存済みの MVT（`z/x/y.pbf`）だけから読む取得元（通信しない）
- 注入 A: `ViewExtentImageStyle`（`BaseStyle`）と `ViewExtentImageStyleRenderer`（`ISkiaStyleRenderer`）。`MapRenderer.RegisterStyleRenderer` で登録し、地理範囲のポリゴン 1 つの `GeometryFeature` に付ける。描画は、世界座標の範囲を viewport で DIP 座標へ変換して `DrawImage`。縮小して見るとき（倍率 0.9 未満）はミップマップを使う
- 注入 B: PNG にエンコードして `RasterFeature`（`MRaster`）の `MemoryLayer`（`RasterStyle`）に入れる
- 位置の確認: 画像の中に、緯度経度の目印（緑の十字）を、画像の描画と同じ変換で描く。Mapsui 側には、同じ緯度経度に標識（マゼンタの円）を置く。両者の重心の差を画素で測る

## 位置の整合

### 1. Mapsui の描画結果の画素（ヘッドレス。88 条件 × A/B）

条件: 2 地点（`dense-odori`・`suburb-okadama`）× z15・16・17.4・18・18.7・19（静止）、画像を z17.4・683×610 で描いたまま視点だけ動かす 5 種（パン +60/+40 px、拡大 +0.6、縮小 −0.8、リサイズ 471×294・800×600）、× DPI 100%・125%・150%・200%（`RenderToBitmapStream` の画素密度）。標識 5 点。

| 操作 | 条件数 | 十字の期待位置との最大誤差（A / B） | 標識の最大誤差 |
| --- | ---: | --- | ---: |
| 静止（連続倍率を含む） | 48 | 0.83 px / 0.83 px | 0.09 px |
| パン | 8 | 0.57 / 0.57 | 0.09 |
| 拡大 | 8 | 0.57 / 0.57 | 0.07 |
| 縮小 | 8 | **1.55 / 1.82** | 0.08 |
| リサイズ | 16 | 0.55 / 0.56 | 0.09 |

- 静止の誤差は DPI が上がるほど大きい（100%: 0.23、125%・150%: 0.57、200%: 0.83 px）。画像が物理ピクセルで 1:1 に近いため、DIP では約 0.4 px 以下
- 基準（静止・パン・拡大・リサイズは 1.0 px、拡大縮小は倍率差ぶん緩め）を超えたのは、**縮小 −0.8 段 × DPI 200% の 4 件**（A・B とも。誤差 1.5〜1.8 px）。ミップマップを使っても 1.55 px で、原因は未特定（内容なしの背景だけでも同じため、地図の内容の影響ではない）
- A と B で位置は同じ（どちらも同じ変換で置かれる）

### 2. 実アプリの画面キャプチャ（DPI 100〜175%）

実際の `MapControl`（OSM ラスタは無効、保存済み MVT から描いた画像だけ）で、画面をキャプチャして、**十字の交点と標識の重心の相対ずれ**を測った。期待位置やキャプチャの原点を使わない（DPI による原点の丸めの影響を受けない）。ウィンドウは最前面。標識は 6 点（地図の上の XAML カードで隠れるものは対象外）。

| DPI | 静止 | パン (+50,+30) | 拡大 (+0.5) | 縮小 (−0.6) | 連続倍率 z17.9（描き直し後） |
| --- | ---: | ---: | ---: | ---: | ---: |
| 100% | 0.02 px | 0.06 | 0.28 | 0.58 | 0.25 |
| 125% | 0.09 | 0.23 | 0.25 | **1.05** | 0.18 |
| 150% | 0.03 | 0.86 | 0.69 | 0.51 | 0.17 |
| 175% | 0.29 | 0.29 | 0.21（標識 1 点のみ） | **1.22**（4 点） | **2.86**（4 点） |

- 静止はいずれも 0.3 px 以下。操作中（古い画像を変形して表示）も、多くは 1 px 以下
- 残る外れ値: **縮小表示の 1.05〜1.22 px、175% の連続倍率 2.86 px**。後者は、画面が小さく（375×270 DIP）、標識の一部が地図の上の XAML カードに近いため、測定の影響の可能性があるが、**未確認**
- 実アプリの密度は、ウィンドウの DPI と少し違うことがある（175%: ウィンドウ 1.75、Mapsui の `GetPixelDensity()` は 1.7473。キャンバスの画素数 ÷ DIP 幅の丸め）。**画像の寸法と変換は、Mapsui の密度で求める**（ウィンドウの DPI を使うと、約 1 px ずれる）
- 表示スケールの変更は、許可を得て一時的に行い、両方のモニターを 100% に戻した。**200% は、この端末のモニターに選択肢がなく、実アプリでは未計測**（ヘッドレスでは 200% を確認済み）

### 3. 画像の描画時間（ヘッドレス。参考）

画像 1 枚（683×610）の描画は、中央値 約 27 ms（95 パーセンタイル 約 170 ms、最大 約 350 ms。最大は初回の JIT・スタイル初期化）。実アプリでは、初回 約 115 ms、2 回目以降 約 27〜38 ms（DPI 100〜175%）。**P2 では、これを背景スレッドへ出し、操作中は古い画像を変形して表示する前提**。

## 注入方式の比較（683×610・z17.4・DPI 100%）

| 観点 | A: カスタムスタイルレンダラー | B: `RasterFeature` |
| --- | --- | --- |
| 位置の整合 | 同じ | 同じ |
| 画像を置く費用 | **約 0 ms**（`SKImage` を持つだけ） | **約 20 ms**（PNG エンコード。683×610） |
| 新しい画像の置き換え〜最初の描画 | 約 2.9 ms | 約 23 ms（エンコード＋Mapsui 側のデコード） |
| 1 フレームの描画（キャッシュ後） | 2.8 ms（線形補間）／**0.47 ms**（1:1 のとき最近傍） | 0.11 ms |
| メモリ | 画像 1 枚（生のピクセル） | PNG のバイト列＋デコード済みの画像 |
| 補間・ミップマップ・ライフサイクルの制御 | 自分で決められる（縮小時はミップマップ、`SKImage` の参照カウントで管理） | Mapsui 任せ |
| Mapsui への依存 | 公開 API（`RegisterStyleRenderer`・`ISkiaStyleRenderer`・`BaseStyle`）。**Mapsui の更新で壊れうる**ため、回帰テストを置く | 標準機能 |

**A を採る案**。B は 1 フレームが軽いが、更新のたびに約 20 ms（UI スレッドを塞がない設計でも CPU を使う）かかり、メモリも二重になる。A の 1 フレームの費用は、1:1 の最近傍で B に近づけられる（ただし、操作中の小数ピクセルの移動では、最近傍だとスナップが出るため、線形補間との使い分けが要る。**P2 で、実際のフレーム時間（P0 の指標）で決める**）。

## 未解決・未確認

- **縮小表示のずれ（1.05〜1.8 px）と、175% の連続倍率のずれ（2.86 px）の原因**: 未特定。操作中の一時的な表示で、体感できる大きさ（約 1 DIP）ではないが、P2 で、画像を描き直したあとの値と合わせて再確認する
- **実ウィンドウのリサイズ**: ヘッドレスの寸法違いでのみ確認。実際のリサイズ操作（ウィンドウ・ペインの境界）は未確認
- **回転**: 対象外（現行の地図は回転しない前提）
- **DPI 200%（実アプリ）**: この端末で選べない。別の端末か、ヘッドレスの結果で代替
- **複数の取得ズーム・実タイルの欠落・通信**: P3 の範囲
- **Svg.Skia（SkiaSharp 3.x 向けにビルドされた Mapsui の依存）**: この確認の経路で SVG を使ったかは未確認（関門の記録と同じ）
- **MVT の固定データは 3 地点の z14 のみ**（9 タイル × 地点。計 23 タイル、約 6.6 MB）。リポジトリには入れず、ハンドオフに保管した（`handoff/poc-p1-mvt/`）。取得元は OpenFreeMap の `planet/20261018_080001_pt`

## photo-map-studio 側に要る変更（P2 以降の提案）

1. **連続倍率の入口**: `VectorMapRenderer.RenderToCanvasAsync` の `zoom` を `double` にする（実証済み: `ViewExtentVectorRenderer`）。取得ズームは整数、表示倍率は連続。スタイルの判定には `floor(zoom)`
2. **画素密度（DPI）の入口**: 画像の寸法は物理ピクセル。**呼び出し側が、Mapsui の実際の密度で寸法を決められる**ようにする（ウィンドウの DPI との丸めの差があるため）
3. **画像（`SKBitmap`／`SKImage`）の所有**: 描いた画像の所有権と、`SKImage` の参照カウントによる解放を、契約として決める
4. **キャンセル**: `CancellationToken` は既にある。P2 の「実行中の描画は原則完走」に合わせて、途中経過の扱いを決める
5. **スタイルのプロファイル**（道路名の優先など）、**ラベル配置の継続性**（操作のたびにラベルが飛ばない）は P2 以降
