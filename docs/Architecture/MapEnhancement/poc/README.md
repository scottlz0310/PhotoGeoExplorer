# ベクター地図レンダラー PoC: P0 比較基準（#293）

[02-vector-renderer.md](../02-vector-renderer.md) の P0「比較基準の固定」の成果物です。**現行版（Mapsui のラスタタイル）の見た目と操作性能の基準**を、再現できる手順と数値で固定します。P1 以降の PoC は、この手順を同じ条件で実行し、現行との差分で採否を判断します。

> [!NOTE]
> 計測の入口（ハーネス）のコードは、スパイクブランチ `spike/293-p0-bench` にあり、**`main` へはマージしません**（#293 の進め方）。この文書は、取り込んだコードを含まない別ブランチで `main` に入れます。

## 固定した条件

| 項目 | 内容 |
| --- | --- |

| ハーネスのコミット | `spike/293-p0-bench` の `65b5817`（`PGE_BENCH_OUT` が設定されたときだけ動く入口と、実行・集計のスクリプト）。基準値はこのコミットで採取した |

### 操作手順（1 地点ごと）

1. **写真選択（ジャンプ）**: 遠い場所（z10）から、`SetMarker` で地点へ移動し z18 にする。確定描画までの時間を測る。基準画像 z18 を保存
2. **ズームの切り替え**: z15・16・17・18・19 へ、それぞれ 2 段階離れたズームから移る。確定描画までの時間を測る。基準画像 z16 を保存
3. **連続ズーム**: z15→z19 を 150 回の操作（約 2.5 秒）で連続して拡大する。フレーム間隔・描画時間・入力から描画までの遅延を測る
4. **パン**: z17 で、1 回の操作ごとに 6 px、150 回（約 900 px）移動する。同じ指標を測る
5. 全地点のあと、**最初の地点へ戻る（再訪）**。同じプロセス内のメモリキャッシュでの確定描画を測る

パン・ズームは、マウスの合成入力ではなく Mapsui の `Navigator` を直接呼ぶ（入力の再現性を優先。入力イベントの経路の遅延は含まない）。

### キャッシュ条件

| 条件 | 内容 |
| --- | --- |
| コールド | プロセスを新しく起動し、タイルのディスクキャッシュを空にして始める（通信を含む）。**1 回**（ネットワークのばらつきが大きく、複数回は意味が薄い） |
| ウォーム | プロセスを新しく起動し、前の実行で溜まったディスクキャッシュで始める（通信なし）。**小ペイン 5 回・大ペイン 4 回** |
| 再訪 | 同じプロセス内で最初の地点へ戻る（メモリキャッシュ） |

### 指標の定義

- **ネットワーク完了**: 操作の開始から、タイル取得（`TileLayer.Busy`）が止まるまで
- **鮮明な画像**: 取得が止まったあと、1 回描画が完了するまで（取得完了後に再描画を 1 回強制して測る）。**ウォームでは約 1〜2 フレーム（16〜32 ms）が測定の下限**
- **描画間隔**: 連続する描画の開始時刻の間隔。60 fps なら約 16.7 ms
- **描画時間**: `IMapRenderer.Render` 1 回の所要時間（既存の描画を包んで記録するだけで、描画内容は変えていない）
- **入力→描画**: 操作の発行から、その操作を含む描画の完了まで
- **50 ms 超の停止**: 描画間隔が 50 ms を超えた回数

## 手順の再現

```powershell
# 1. 計測のブランチでビルド（現行版の基準を採る場合は、aed2a1a にハーネスを足した状態）
git switch spike/293-p0-bench
dotnet build PhotoGeoExplorer/PhotoGeoExplorer.csproj -c Release -p:Platform=x64

# 2. 実行（コールド 1 回 → ウォーム n 回）。-LargeMap で地図を大きな領域へ、-Record で録画（ffmpeg が要る）
$exe = '<…>\PhotoGeoExplorer.exe'
pwsh -File .\scripts\poc\Invoke-MapBench.ps1 -Label cold-1 -ExePath $exe -OutDir <out> -CleanCache -Record -Commit '<記録するコミット>'
pwsh -File .\scripts\poc\Invoke-MapBench.ps1 -Label warm-1 -ExePath $exe -OutDir <out> -Commit '<記録するコミット>'   # 以降 warm-2, warm-3, ...

# 3. 集計（Markdown の表）
pwsh -File .\scripts\poc\Summarize-MapBench.ps1 -Dir <out>
```

- スクリプトは、設定ファイル（`settings.json`）を退避し、計測中だけ空のフォルダーを開く設定にして、終了後に必ず元へ戻す（アプリはウィンドウを閉じるときに設定を保存するため）。
- 計測中は、ウィンドウを最前面にして録画する。他の作業（マウス操作など）はしない。
- PoC は、同じ入口（`PGE_BENCH_OUT`）と固定手順で、PoC のビルドに対して実行する。ハーネスは、`MapControl.SetMapRenderer` で描画を包む構成なので、PoC が描画の経路を変える場合は、計時の位置を合わせて見直す。

## 基準値（現行版）

全数値は [小ペイン](baseline-current-small-pane.md)・[大ペイン](baseline-current-large-pane.md) に、生データ（JSON）は [baseline/results/](baseline/results/) にあります。基準画像（800×600）は [baseline/images/](baseline/images/) にあります。操作録画は、容量と個人の環境の映り込みを避けるため、リポジトリには入れていません（採取者のハンドオフに保管）。

### 要点（ウォーム。中央値、括弧は最小〜最大）

| 項目 | 小ペイン（471×294） | 大ペイン（683×610） |
| --- | --- | --- |
| 描画間隔 p50（パン・連続ズーム） | 16.0〜16.1 ms | 16.0〜16.1 ms |
| 描画間隔 p95 | 約 20〜22 ms | 約 20〜22 ms |
| 描画間隔 最大 | 約 24〜28 ms | 約 24〜27 ms |
| 50 ms 超の停止 | 0 回 | 0 回 |
| 描画時間 p95 | 0.9〜1.9 ms | 1.4〜3.6 ms |
| 入力→描画 p95 | 約 10〜11 ms | 約 11〜14 ms |
| 確定描画（ジャンプ。鮮明な画像） | 約 29〜32 ms（下限付近） | 約 30〜32 ms（外れ値あり） |
| コールドのジャンプ（鮮明な画像） | 約 110〜285 ms | 約 350〜470 ms |
| ワーキングセット | 約 264〜282 MB | 約 291〜295 MB |

- **現行は 60 fps を維持し、50 ms を超える停止がない。1 回の描画は数 ms 以内**で、PoC が比べられる余白は小さい（PoC は表示範囲全体を 1 枚で描くため、描画時間が現行の 1 回あたり 1〜3 ms より大きくなる。操作中の追従は、直前の画像の変形表示で保つ設計）。
- 大ペインのウォームのジャンプで、外れ値が 2 件あった（別の地点・別の実行。約 95〜240 ms。他の実行は約 15 ms）。ディスクキャッシュの読み込みや GC の影響の可能性があるが、**原因は未特定**。

### 計測の限界

- **DPI は 100% だけ**。150%・200% は、この端末の表示スケールを変える必要があるため、P0 では採っていない。別の端末か、表示スケールの変更の許可を得たときに採取する。
- コールドは 1 回のため、ネットワークの時間のばらつきは評価できない。
- パン・ズームは `Navigator` の直接呼び出しで、ポインター入力の経路の遅延を含まない。
- 地図の上には、写真未選択を示す XAML のカード（「写真を選択してください」）が重なって映る（Skia の描画の外にあるため、計測の対象外）。
- 確定描画の「鮮明な画像」は、取得完了後の再描画で測るため、ウォームでは 1〜2 フレームが下限になる。差が 1 フレーム以内の比較はできない。
- GPU の使用率・CPU 時間は未計測（ワーキングセットと GC ヒープのみ）。

## 許容差（案。合意待ち）

> [!IMPORTANT]
> P0 の完了には、許容差が決まっていることが必要です。以下は、基準値のばらつき（ウォームの最小〜最大）から出した**案**で、採用前に合意を取ります。**数値は補助。体感できる退行があれば、数値内でも不合格**（#293）。

| 項目 | 許容差（案） | 根拠 |
| --- | --- | --- |
| 描画間隔 p50 | 現行 +1 ms 以内（約 17 ms 以下） | 60 fps の維持。現行のばらつきは 0.2 ms 以内 |
| 描画間隔 p95 | 現行ウォームの最大 +3 ms 以内（約 25 ms 以下） | 現行の最小〜最大の幅は約 2〜3 ms |
| 描画間隔 最大 | 現行ウォームの最大 +10 ms 以内（約 40 ms 以下） | 現行の最大は約 23〜32 ms |
| 50 ms 超の停止 | 0 回（現行と同じ） | 現行は 0 回。1 回でも出れば要調査 |
| 入力→描画 p95 | 現行ウォームの最大 +5 ms 以内（約 19 ms 以下） | 体感の遅延に直結。現行のばらつきは約 2〜4 ms |
| 確定描画（ウォームの再訪・ジャンプ） | 現行 +1 フレーム（約 17 ms）以内 | 測定の下限が 1〜2 フレームのため、それ未満は区別できない。補助目標は p95 200 ms 以下 |
| 確定描画（コールド） | 現行の +20% 以内（通信待ちを除く描画分で比べる） | ネットワークのばらつきが大きく、描画分を分けて比べる |
| メモリ（ワーキングセット） | 現行 +25% 以内、かつ繰り返し操作で単調増加しない | 現行は約 265〜295 MB。PoC は大きな画像とキャッシュを持つため |
| 見た目 | 基準画像との差分の目視（道路名・主要ラベル・ピン・出典の欠落や位置ずれがない）。画素の一致は求めない | 描画エンジンが違うため、画素単位の一致は不可能 |
| 位置の整合 | ピンと背景の位置ずれ 0（パン・ズーム・リサイズで目視と座標で確認） | 正しさの項目 |

**この案で決めたいこと**: 描画間隔・入力遅延を「現行のばらつき + 小さな余白」で縛る（現行より遅くなることを許す根拠にしない）一方、メモリは構造上増えるため +25% を許す、という方針でよいか。
