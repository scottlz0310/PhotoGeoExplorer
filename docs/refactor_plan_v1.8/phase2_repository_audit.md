# Phase 2: リポジトリ監査ガイド

> 作成日: 2026-04-11
> 前提: [phase1_ideal_architecture.md](./phase1_ideal_architecture.md)
> 位置づけ: Phase 1 の理想定義に対する現行コードベースの差分監査

---

## 1. 目的

本ドキュメントは、PhotoGeoExplorer リポジトリ全体を対象に、MVVM 境界違反とテスト不能要因を監査するための実施ガイドである。

目的は次の 3 点に限定する。

1. ルール違反を根拠コードつきで列挙する。
2. テスト可能性を阻害している構造を優先度つきで可視化する。
3. Phase 3 の Issue 分割に耐える粒度で修正対象を整理する。

本 Phase では**コード変更を行わない**。

---

## 2. 監査対象

### 2.1 対象範囲

- `PhotoGeoExplorer/`
- `PhotoGeoExplorer.Core/`
- `PhotoGeoExplorer.Tests/`
- `PhotoGeoExplorer.E2E/`

### 2.2 重点領域

以下は優先的に確認する。

1. `MainWindow.xaml.cs`
2. `Panes/*`
3. `Services/*`
4. `State/*`
5. `PhotoGeoExplorer.Core/*`

### 2.3 除外

次は監査対象外とする。

- 自動生成コード
- バイナリ
- 一時生成物

除外した場合は、その理由を監査結果に明記する。

---

## 3. 監査単位

監査は次の単位で行う。

1. ファイル単位
2. クラス単位
3. 必要に応じてメソッド単位

原則として「問題の所在が特定できる最小単位」で記録する。
1 ファイルに複数カテゴリの違反がある場合は分けて記録する。

---

## 4. 検出カテゴリ

### 4.1 MVVM 境界違反

検出対象:

- ViewModel から UI 型を参照している
- View に処理本体が残っている
- Model / Core からインフラや UI に依存している
- MainWindow に機能別ロジックが残っている

証拠として記録する内容:

- ファイルパス
- クラス名
- 問題のコード断片
- Phase 1 のどのルールに違反したか

### 4.2 テスト不能要因

検出対象:

- `new` による直接依存
- static 依存
- hidden dependency
- コンストラクタを通らない依存取得
- テストから完了待機できない非同期

### 4.3 非同期不整合

検出対象:

- `async void` の誤用
- fire-and-forget
- キャンセル不能な長時間処理
- 例外黙殺
- UI スレッド前提でしか成立しない実装

### 4.4 構造的問題

検出対象:

- Service が存在せず ViewModel または View に副作用が滞留している
- 巨大 Service に責務が集中している
- 同種ロジックが複数箇所へ重複している
- 形式上は MVVM だが実態としてコードビハインド駆動である

### 4.5 禁止判断

以下の理由による違反無視は禁止する。

- 「小さい問題なので無視」
- 「他で吸収されている」
- 「動いているから問題ない」
- 「将来対応予定」

すべての違反は記録対象とする。

---

## 5. 重大度定義

| 重大度 | 条件 |
|---|---|
| Critical | テスト不能で、かつ変更時の機能破壊リスクが高い |
| High | 明確な境界違反または hidden dependency がある |
| Medium | 構造上の負債だが、局所修正で是正しやすい |
| Low | ルール逸脱はあるが即時修正優先度は低い |

重大度は感覚で決めず、影響範囲と修正コストの両方で説明する。

## 6. 監査手順

### 6.1 事前確認

1. Phase 1 文書を監査基準として固定する。
2. 対象ブランチとコミットを記録する。
3. 監査除外対象を明示する。

### 6.2 全体走査

1. `MainWindow` と各 Pane の責務境界を確認する。
2. ViewModel ごとに依存先一覧を抽出する。
3. Service の責務密度と重複を確認する。
4. Core に UI 依存が混入していないか確認する。

### 6.3 詳細監査

各 ViewModel / View / Service について以下を確認する。

- 依存取得方法
- 副作用の所在
- 非同期完了の観測可能性
- エラー処理
- キャンセル経路
- 状態露出方法

### 6.4 取りまとめ

1. カテゴリ別件数を集計する。
2. 重点修正領域 Top 5 を選ぶ。
3. 各 ViewModel のテスタビリティスコアを算出する。
4. Phase 3 の Issue 分割に必要な単位で問題を束ねる。

### 6.5 テスト起点監査

各 ViewModel について、単体テストを書こうとする前提で監査する。

1. 単体テストを記述するために必要な依存関係を列挙する。
2. テストを書けない場合は、その理由を必ず記録する。
3. 理由は以下のいずれかに分類する。

- UI 依存
- 依存注入不可
- 非同期制御不可
- 副作用未分離

この結果は、Phase 3 の最優先修正候補として扱う。

### 6.6 優先順位付けルール

優先度は以下のスコアで決定する。

`優先度スコア = (重大度係数 × 影響範囲) + テスト不能係数`

- 重大度係数
  - `Critical = 5`
  - `High = 3`
  - `Medium = 2`
  - `Low = 1`
- 影響範囲
  - 参照箇所数または依存関係数
- テスト不能係数
  - 完全にテスト不可 = `+5`
  - 部分的に不可 = `+3`
  - テスト可能 = `0`

スコア順に Phase 3 の Issue 優先順位を決定する。

## 7. 証拠記録ルール

1. すべての指摘はコード根拠つきで記録する。
2. 「おそらく」「たぶん」などの推測表現は禁止する。
3. 根拠コードは違反を説明する最小限の範囲に留める。
4. 同じ根拠で複数ルール違反を主張する場合は、主違反を 1 つに絞り、残りは関連事項として記録する。
5. 既存テストが存在する場合は、そのテストで観測できない理由も記録する。

---

## 8. テスタビリティスコアリング

各 ViewModel に 100 点満点でスコアを付与する。

初期値は 100 点とし、以下を減点する。

| 項目 | 減点 |
|---|---|
| UI 型への直接依存 | -30 |
| 具象 Service の直接生成 | -20 |
| static 外部依存 | -15 |
| hidden dependency | -15 |
| fire-and-forget | -15 |
| `async void` の誤用 | -10 |
| `System.IO` 等の直接 I/O | -20 |
| 状態が外部から観測不能 | -10 |
| キャンセル経路がない | -10 |
| 例外黙殺 | -10 |

補正ルール:

- 0 点未満にはしない。
- 同一原因の重複減点は避ける。
- スコアと重大度の整合が取れない場合は説明を付す。

### 8.1 スコア解釈

| スコア | 解釈 |
|---|---|
| 90-100 | 単体テスト容易 |
| 70-89 | 軽微な改善でテスト容易化可能 |
| 40-69 | 依存整理が必要 |
| 0-39 | 構造的リファクタリング優先 |

## 11. Phase 3 への接続ルール

Phase 3 では、監査結果をそのまま Issue 化しない。
以下の条件を満たす単位に再編してから Issue 化する。

1. 1 Issue あたり 1〜2 日で完了できる。
2. 1 Issue あたり最大 5 ファイル変更を目安にする。
3. 横断変更は段階分割する。
4. 修正後にビルド可能である。
5. 対応後にテスト可能性が上がることを説明できる。

### 11.1 Issue 分解ヒント

以下の単位で問題を束ねること。

- ViewModel 単位で閉じる変更
- Service 単位で閉じる変更
- 1 つの違反タイプに限定した変更

禁止:

- 複数 ViewModel をまたぐ同時修正
- UI + Service + Core の同時変更

---

## 12. 完了条件

監査完了と見なす条件は以下のとおり。

1. 重点領域を含む全対象範囲の確認が終わっている。
2. すべての指摘にコード根拠がある。
3. カテゴリ別件数と重大度別件数が集計されている。
4. ViewModel ごとのスコアが算出されている。
5. Phase 3 に渡せる修正単位の示唆がある。

未確認領域がある場合は、監査完了ではなく「暫定結果」と明記する。
